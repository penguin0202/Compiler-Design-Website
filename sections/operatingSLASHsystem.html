Operating/System

At the hardware level, the Central Processing Unit (CPU) will execute any instruction it is given via electrical signals (basic low-level instructions like storing variables by value; will be elaborated in the next/assembly section !!!!!!). A collection of instructions to the CPU that performs some type of function, whether that is an image editor to, well, edit images, or a videogame for entertainment, is what's called a "program".

And Operating Systems, like Microsft's Windows and Apple's Mac, are actually just programs.

I say "actually just" because some, like me, might have thought operating systems were...different from regular "programs". After all, it's the first thing that pops up after turning the computer on, so it must be something that's embedded into the computer's hardware or something, and not a software program. Plus it can't be just a a bunch of instructions sent the CPU if it's something you run custom bunches of instructions like videogames ON, right? These are very valid doubts, and I will trace the Operating System's role in a computer in a moment, but first, how about a question:

What is something Operating Systems can do that programs running on them cannot?

The layout of the Desktop? Equivalent to just buttons used in every app but just with custom images on top for the thumbnail. The taskbar at the bottom of the screen that one can navigate across one's open apps? Not much different from the tabs on top of browsers like Google Chrome to get to other websites. The ability to download outside apps and run them? You can download extensions for syntax highlighting for different programming languages in Visual Studio Code editor and enable them. Well how about the hacker-type stuff like the command prompt that modifies the system? Well Minecraft's slash commands in text chat (like "/spawn ..." or "/tp @...") aren't all that dissimilar, given that they modify the world or the player in some way.

Really, other than using physical memory (oops spoilers), Operating Systems aren't different from regular programs. They're merely a special type of program that has the ability to encompass all others.

And since they are just programs, they too are comprised of instructions. Way simplifying here, but you could think of an Operating System as just code on a USB stick (which stores data, like computers, in electric signals) that is then plugged into the CPU to run once the computer turns on; which is actually why there's a splash screen when the computer is just booting up--it's the O.S. waking up and getting everything set up.

Once the computer and operating system turns on, the desktop, file explorer, and other background processes begin doing their work. I don't quite know what the background processes do (as the jobs of an O.S. are quite complex), but I do know at least one of them allows for the surfing of the internet. And through the internet, let's say, the user downloads programs like Discord, OBS Studio, or Minecraft, and was inspired to create their own program. So they write their code in a language of their choice in a code editor they've downloaded, runs it through the compiler specified to that langauge to generate machine-readable instructions, and.....and what? How does the Operating System "run" the code?

Well, it's not all that incorrect to say that it already kind of did. Bear with me here:

The Operating System has a lot of jobs, one of which is a babysitter. Because normal developers aren't that equipped to deal with hardware level (low-level) instructions, especially when it comes to storing variables at specific memory addresses and handling the CPU when multiple programs need it at one time to perform each of their tasks, the Operating System is created to do all of that automatically. The O.S. is essentially a bridge between software and hardware: whenever a program needs to do some addition, division, bit manipulation, file input output, storing values in memory, or anything that involves the CPU, it quote sends unquotes the instruction to the Operating System, and let it do with it how it pleases. That's not how I wanted to phrase it, but the gist is that regular programs don't interact with the hardware directly, they actually interact with the Operating System only, with it then interacting with the hardware with the program's given instructions. And the reason that our programs have to go through the Operating System is because the O.S. knows what it is doing--it helps debug and catch critical errors your programs might have. Examples of such errors include the much dreaded "Segmentation Fault", where the program reads or writes memory where it doesn't have access (such as another program's memory), "File not found" when accessing a non-existent file (probably due to typing the wrong filename), "Permission Denied" if the Operating System implements the ability to lock files behind users, "Division by 0", which is actually an error modern CPUs catches, but is still reported to the user via the Operating System, infinite while loops which is technically not an error, but isn't what anybody should want, and the very rare/occasional "Out of Memory" for when you've taken too many screenshots and run out of storage.

The most common types of errors the Operating System helps prevent are systemic, memory-related errors, and I wanna draw 3 connections from that: (1) this is the difference between Operating Systems and regular programs--the Operating System is a program that execute instructions and manage memory at the hardware level, while regular programs do so in a software level, in a sort of simulated memory (a "virtual memory", if you will), that is then dispatched to the O.S. for actual execution; (2) that it is very important Operating Systems exist to serve as safety nets for developers to prevent bad code getting to the level of hardware where there's no turning back (since the CPU will execute whatever instruction you give it; thus the remark of babysitter), and that is why there are so few mainline Operating Systems people use, because it takes a lot of (difficult/hard) work to ensure all bases are covered, and is also why a big team is behind major and feature-filled ones; and (3) the fact that pretty much only memoric errors could take place at this stage means the compiler actually did a lot of heavy lifting (finally brings it back to compilers, this guy). The compiler makes sure assigning undeclared variables gets thrown an error, functions get the correct number of arguments, of no duplicate variable naming, etc before converting the source code gets turned into machine instructions, so the Operating System doesn't have to.

What was I talking about again? Oh right how the O.S. runs code. Yeah since the O.S. is in fact a running program, (technically already part of the O.S. code, )all you need to do run your custom program is to tell the O.S. to add it to its programming. You can either do that (using Windows as an example) by double-clicking on an .exe icon in your folders, or run ".\MY_PROGRAM.exe" in the command prompt; both of which works because the interfaces--desktop or file explorers and command prompt--are already all part of the O.S. (desktop and file explorers in particular function just like buttons in app that signals the app do something), so the O.S. would automatically get the information that it should load the .exe's code into its own.

But Operating Systems can't just sequentially add programs' code, that'll only allow it to run one program at one time (which is not what they do since I can both talk to my friends on Discord and record Valorant gameplay on OBS Studio at one time!), and that's where a thing called "CPU Scheduling" comes in. Ok I may have mislead you before, the O.S. doesn't really "add code to its programming", it more so disperses lines of code in between the long list of instructions it has the CPU run every nanosecond. Huh..In trying to correct myself, I've adequately described what I wanted to talk about next, yes, "[dispersing] lines of code in between the long list of instructions [the O.S.] has the CPU run every nanosecond" is exactly what CPU Scheduling is! CPU Scheduling is yet another job of the Operating System. It is intended to be a way to run multiple programs (seemingly to the human eye) concurrently by dividing each program's code that the O.S. receives and the CPU is to run into smaller segments and inserting them into a different place in memory where the CPU gets inputted the instructions.

And..That's it folks. Let's recount the steps we took to run code:

  1. Developer writes (high-level) code for a program in a code editor in a selected programming language
  2. Compiler translates that code into (executable) binary instructions through some process I will talk about, all the while checking for any compile-time errors (BTW REFERENCE THIS LINE THE NEXT SECTION AND TALK ABOUT LOW-LEVEL INSTRUCTIONS LIKE ASSEMBLY).
  3. O.S. receives the instructions (either by the developer double-clicking on the resulting .exe binary file created by the compiler, or the compiler automatically running the run command in the command prompt program) and, whilst catching run-time errors like segmentation faults, then sprinkles them throughout the list of instructions the CPU already needs to do (a process called CPU scheduling). Which they can do because they are the first program to run and only to interact with the hardware, giving them whole access and control over the CPU (search kernel mode and operating rings/accesses in programming for more info)
  4. CPU, maybe interacting with other components of hardware like the monitor or the sound system, executes those instructions

And oh my stars and garters. A program runs.
